# v1.3 준비 P0-01: thread generation 정확성 검증

날짜: **2026-10-11, Asia/Seoul**. 기준 commit `70d6771` 이후 수정.
**P0-01 구현과 검증 완료. P0-02의 로컬·hosted gate PASS, 정식 수락은 pending.**
패키지 버전은 `1.2.0rc1`이며 이 문서는 stable v1.2 또는 v1.3 릴리스 선언이 아니다.

## 실제 재현과 수정

현재 소스로 새 `build-v13-generation-before`를 만들어 기존 `fd_slot_reuse 80`을
`events=8,threads=2`에서 실행했다. target은 정상 종료했지만 slot 1의 generation=80,
event_count=160, retained=2였고 event slots 2–7이 unpublished로 판정되었다.
별도 비계측 controller/계측 worker fixture에서도 `events=8,threads=1`로 재현했다.
원인은 재사용 시 sequence만 0으로 돌아가고 event_count는 누적되는 것이었다.

수정 후 같은 기존 fixture에서 generation=80, event_count=2, retained=2,
snapshot stable=true, unstable_records=[]를 확인했다. **complete는 false를 유지한다.**
이전 79세대의 기록이 보존되지 않기 때문이다.

- `FD_THREAD_GENERATION_COUNT`로 event_count/sequence가 현재 세대 범위임을 표시한다.
  재등록 시 event_count를 0으로 초기화하며 ABI v1의 크기·offset은 바꾸지 않는다.
- `dropped_count`는 슬롯 수명 동안 누적된 세대 내 ring eviction 수를 보존한다.
  이전 세대의 overflow를 마지막 세대의 초기화로 숨기지 않는다.
- `FD_THREAD_HISTORY_RETIRED`와 sticky `FD_STATUS_PARTIAL`로 이전 세대 기록의 부재를
  노출한다. 새 decoder는 `retention`을 제공하며 과거 이벤트 수는 unknown/null이다.
- 같은 sequence/publication으로 세대가 바뀌는 event copy도 안정된 기록으로 수락하지 않는다.
- generation이 UINT32_MAX인 슬롯은 재사용하지 않고 overflow/partial을 알린다.
- fault flow에 `retired_thread_generations` gap을 추가한다. TID=0인 종료된 슬롯의
  과거 TID나 이전 세대 스택은 재구성하지 않는다.

계약은 [ABI 문서](format.md#thread-generation-retention)에 있다.

경로가 `build-*`로 시작하는 근거는 **로컬 실행 산출물이며 커밋 대상이 아니다**.
현재 source로 실행한 결과다. hosted 결과는 아래에 revision과 실행 링크를 별도로 기록했다.

18 native cases는 events=1/8/4096 각각 workers=1/80/10,000, 2슬롯 재사용,
64슬롯 두 세대, wrap 두 용량, 이전 세대만 overflow한 뒤 마지막 세대 정상 기록,
세 용량의 80번째 세대 SIGILL, UINT32 generation exhaustion이다.
모든 설정의 전체 Cartesian 조합을 실행했다는 의미는 아니다. controller는 계측하지
않아 threads=1에서도 worker가 실제 슬롯을 재사용한다. raw oracle는 고정 ABI 크기와
offset으로 직접 읽고 current generation의 publication/sequence/type/address를 비교한다.

legacy reader는 추가 flags와 retention을 모른다. 실제 비교에서 첫 세대는 stable/complete,
80번째 세대는 stable/incomplete였으며 현재 reader와 같은 이벤트를 반환했다.
older reader가 전체 과거 기록을 complete라고 잘못 수락하지 않는 경로를 확인했다.

추가 native acceptance의 최초 실행은 launcher/oracle 환경변수가 없어 NOT RUN이었다.
`build-v13-p0-acceptance-results/report.json`에 보존했으며 제품 테스트 실패로 계산하지
않는다. 아래처럼 launcher, runtime, 독립 oracle를 지정해 별도 출력 경로로 재실행한
결과가 517/517 PASS다. compiledb 검사도 최초 기본 PATH에서는 NOT RUN이었으며
준비된 별도 compiledb 환경과 Clang 절대 경로를 지정한 실제 검사 결과를 표에 기록했다.

### 통합 검증에서 추가 수정한 compiler 선택

첫 core/gRPC release profile은 설치된 wheel의 doctor에서 FAIL했다.
native build에는 `--cc/--cxx`로 Clang 절대 경로를 전달했지만 wheel consumer가 이를
무시하고 기본 PATH의 clang을 선택했기 때문이다. 이 호스트의 기본 PATH에는 해당
compiler가 없었다. 최초 실패 보고서는 `build-v13-p0-core/report.json`과
`build-v13-p0-grpc/report.json`에 보존했다.

`test/v12_release_gate.py`의 소비자 환경을 동일한 ns.cc/ns.cxx로 수정했다.
다른 toolchain으로 대체하거나 FAIL을 PASS로 바꾸지 않았다. 새 디렉터리의 최종
profile에서 모든 required row와 실제 설치된 doctor가 통과했다.

## 재실행 명령

저장소 루트, 준비된 Python 3.12/Clang 18/Docker 환경에서 실행한다. 출력 경로와
Docker image tag는 기존 자료와 충돌하지 않게 새 이름을 선택한다.

```sh
.venv/bin/python test/v12_release_gate.py --profile core \
  --cc "$PWD/.tools/clang/usr/bin/clang-18" \
  --cxx "$PWD/.tools/clang/usr/bin/clang++-18" \
  --build-dir build-v13-p0-core-final --install-prefix build-v13-p0-core-final/install \
  --work-dir build-v13-p0-core-final/release-work --output build-v13-p0-core-final/report.json
.venv/bin/python test/v12_release_gate.py --profile grpc \
  --cc "$PWD/.tools/clang/usr/bin/clang-18" \
  --cxx "$PWD/.tools/clang/usr/bin/clang++-18" \
  --build-dir build-v13-p0-grpc-final --install-prefix build-v13-p0-grpc-final/install \
  --work-dir build-v13-p0-grpc-final/release-work --output build-v13-p0-grpc-final/report.json
.venv/bin/python test/thread_generation_contract.py \
  --binary build-v13-p0-core-final/test/fd_thread_generation \
  --output build-v13-p0-core-final/thread-generation-recheck.json
FD_LAUNCHER="$PWD/.venv/bin/python -m faultdebug.cli" \
FD_ORACLE="$PWD/.venv/bin/python $PWD/test/oracle.py" \
FAULTDEBUG_RUNTIME_DIR="$PWD/build-v13-p0-acceptance" \
  .venv/bin/python test/run_tests.py --suite acceptance \
    --build build-v13-p0-acceptance --output build-v13-p0-acceptance-final-results
docker build -f test/shop/Dockerfile -t faultdebug-shop:v13-p0 .
.venv/bin/python test/shop/run.py --image faultdebug-shop:v13-p0 \
  --processes 8 --requests 4 --concurrency 2 --port 8863 --output build-v13-shop-n8
.venv/bin/python test/shop/run.py --image faultdebug-shop:v13-p0 \
  --processes 16 --requests 24 --concurrency 4 --scenarios success payment_decline \
  --port 8864 --output build-v13-shop-n16
```
